# 3. Підхід до специфікації вимог: від сценаріїв одного UC, а не повний формальний опис

**Status:** Accepted

## Context
Умови: ER-модель із Завдання 1 зафіксована й здана; це MVP; завдання вимагає порядку UC → сценарії → вимоги й глибини в одному прецеденті.

## Decision
1. Уточнюємо вимоги від сценаріїв: EARS-вимоги пишемо лише для сценаріїв UC «Виставити оцінку» та для правила доступу Студента (UC «Переглянути успішність», REQ-7 / S6).
2. Усе інше (створення занять, перегляд успішності вглиб, автентифікація, історія змін, AES-256) явно виносимо в «Поза обсягом» з причиною.
3. Правила доступу (REQ-5, REQ-7) — функціональні вимоги EARS, а не NFR. NFR описують лише якості системи: сумісність, навантаження, продуктивність, мову.

## Alternatives considered
* **Повний формальний опис усіх UC системи наперед.** Відкинуто: вимоги без сценаріїв не перевіряються тестами, обсяг неспівмірний із завданням, зростає ризик розбіжностей з ER. Ціна рішення: решта UC лишаються без вимог.
* **Лише user stories без формальних вимог.** Відкинуто: двозначність, немає однозначної трасування «вимога ↔ сценарій»; за завданням user story й так записується як Gherkin-сценарій.
* **Правило доступу Студента як NFR (403 на 100% запитів).** Відкинуто: це поведінка системи у відповідь на запит, а не якість; перевіряється функціональним сценарієм.

## Consequences
* Кожна вимога має сценарій, матриця трасування перевіряється механічно.
* Інші UC в майбутньому додаються за тією ж процедурою: UC → сценарії → вимоги → рядки матриці.
* До розписування решти UC система не має повної специфікації — це відоме обмеження MVP.
