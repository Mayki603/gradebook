# 6. Архітектура: горизонтальні шари, великий компонент Backend, інтерфейси на межах

**Status:** Accepted

## Context
Завдання 5 вимагає діаграму компонентів власної системи, узгоджену з даними (ER, Завдання 1), вимогами (Завдання 2), взаємодією (Sequence, Завдання 3) і процесом (BPMN, Завдання 4).
Попередні рішення: учасники Sequence — `GradebookUI`, `GradeService`, `LESSON`, `STUDENT`, `GRADE`, а репозиторії віднесено до архітектури (ADR 0004); автентифікація зовнішня (ADR 0002, п. 4); відсутність відповіді, зокрема 503 від черги NFR-2, обробляється таймером (A3).

## Decision
1. Форма — діаграма компонентів у Mermaid (`architecture.md`) і рендер із неї.
2. Один архітектурний варіант — горизонтальні шари Presentation → API → Services → Data Access → Database, послідовно в усій системі. Великий компонент `Gradebook Backend` об'єднує шари API, Services і Data Access та має порти `pApi`, `pIdp`, `pDb`.
3. Компоненти: `GradebookUI`; `API Gateway` (черга допуску NFR-2); `GradeService`, `IdentityAdapter`; `LessonRepository`, `StudentRepository`, `GradeRepository`, `TeacherRepository`; `Gradebook DB` (усі сутності ER). Учасники Sequence LESSON, STUDENT, GRADE відповідають репозиторіям.
4. Lollipop (provided/required) лише на межах, де є змінний постачальник або споживач: `IGradebookApi` (клієнти web і mobile), `IGradebookDb` (база даних), `IIdentity` (зовнішній провайдер). Усередині backend контракти між шарами — звичайні залежності.
5. Порти — лише там, де компонент має зовнішнє з'єднання: `pApi`, `pDb`, `pIdp`.
6. Зовнішня інтеграція одна — Identity Provider; Email-сервіс явно поза моделлю («Поза обсягом», Завдання 2); брокер повідомлень не потрібен, бо сценарії синхронні, а черга NFR-2 — це черга допуску всередині API Gateway.
7. Припущення: A5 — API Gateway прозорий для сценаріїв Sequence; A6 — `IdentityAdapter` дає «teacherId із сесії» за email; A7 — довідкові сутності наповнюються поза моделлю.
8. Нотація: у Mermaid немає вбудованого socket, тому required-інтерфейс — пунктирна стрілка до кружка з підписом `requires`. Порядок вузлів у шарі задано порядком оголошення залежностей: приховані зв'язки (`~~~`) у Mermaid працюють як ребра й ламають шари.

## Alternatives considered
* **PlantUML component diagram з рідними lollipop і socket.** Відкинуто: у середовищі перевірки не було PlantUML, а GitHub не рендерить його без зовнішнього сервісу; Mermaid рендериться в превью. Ціна рішення: socket лише наближено.
* **Вертикальні модулі (оцінки, ідентифікація).** Відкинуто: усі сценарії Sequence проходять через ті самі шари, окремі модулі не дали б переваг. Ціна: якщо з'являться інші UC, варіант треба переглянути.
* **Змішана архітектура (шари й модулі).** Відкинуто: допустима лише з поясненням, а потреби в ній немає.
* **Lollipop між кожними двома шарами (`IGradeService`, `ILessonRepository`…).** Відкинуто: типова помилка «lollipop на кожному класі»; усередині одного модуля — залежності.
* **Без API Gateway (UI викликає GradeService напряму, як у Sequence).** Відкинуто: немає місця для черги допуску (NFR-2) і перевірки сесії. Ціна: припущення A5.
* **Вхід через редирект браузера напряму до провайдера.** Відкинуто: токени лишаються на сервері, а зовнішнє з'єднання одне — порт `pIdp`. Ціна: компонент `IdentityAdapter`.
* **Брокер повідомлень для черги.** Відкинуто: усі сценарії синхронні, Викладач чекає відповіді (BPMN).
* **Окремий компонент адміністрування й імпорту довідкових даних.** Відкинуто: поза обсягом Завдання 2; наповнення довідкових даних — припущення A7.

## Consequences
* Кожен компонент і залежність трасуються до ER, вимог, Sequence або BPMN (таблиці в `architecture.md`); перевірка — `scripts/check_architecture.py`.
* Якщо з'являться UC адміністрування чи імпорту, потрібні новий компонент і зовнішнє джерело даних.
* Якщо знадобиться точна UML-нотація socket, діаграму треба перенести в PlantUML.
